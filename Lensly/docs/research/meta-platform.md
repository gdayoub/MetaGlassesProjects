# Meta platform findings

Checked 2026-10-22 against current public Meta documentation and repository source. No glasses or mobile SDK were exercised. Every device workflow below is **Not Yet Hardware-Verified**. Confidence refers to documentation, never an end-to-end test.

## Runtime and installation requirements

The current [setup guide](https://wearables.developer.meta.com/docs/develop/webapps/setup/) requires glasses software v125+ and Meta AI app v272+ (update both and the band). Enable Developer Mode from the paired phone's App Info/version area. The [test guide](https://wearables.developer.meta.com/docs/develop/webapps/test/) describes connecting the HTTPS URL through App Settings → Apps → Web Apps → Connect Web App. Menu names may vary with app version.

Glasses need a publicly accessible HTTPS URL with a valid certificate. A Windows loopback HTTP server is suitable for local engineering only. Publishing or starting an external tunnel requires the owner's authorization; it was not performed by this research. Host the application and protected API together when possible to avoid cross-origin complexity. Do not put secrets into an install URL or QR code.

The app can be installed using a supported QR install link; installation still needs wearer confirmation. A resolved `navigator.install()` promise only indicates dispatch, not successful installation. Developer Mode does not override country or account eligibility. [Setup](https://wearables.developer.meta.com/docs/develop/webapps/setup/), [Troubleshooting](https://wearables.developer.meta.com/docs/develop/webapps/troubleshoot/).

## Display design

Use 600 × 600 as a validation viewport, not a fixed layout size. The display adds light to the real scene: black contributes no light. Use a black canvas, readable relative type, clear focus outlines, wrapping text, and bounded surfaces. Give long content one intentional scroll owner or paginate it. Keep controls away from obstructed edges. There is no documented universal pixel safe-area or mandatory font size in the reviewed framework-neutral guide. Test bright and dark surroundings, zoom, long answers, errors, and focus near edges. [Display/layout](https://wearables.developer.meta.com/docs/develop/webapps/build/display-and-layout/).

Use browser history for meaningful destinations. The documented history limit is five entries including the initial document. Avoid adding entries for transient focus changes. The native Back action dismisses the composer before traversing history. [Input/navigation](https://wearables.developer.meta.com/docs/develop/webapps/build/input-and-navigation/).

Meta's UI toolkit is available and Apache-2.0 licensed, but current platform guides explicitly permit semantic HTML without it. Its repository scaffold contains older fixed-size custom-UI examples; follow current platform documentation instead. [Toolkit](https://github.com/facebook/meta-ray-ban-display-ui-toolkit-web), [framework-neutral overview](https://wearables.developer.meta.com/docs/develop/webapps/build/overview/).

## SDK status, distribution, and conflicting documentation

Both official native repositories report 1.0.1, released 2026-10-09. Android 1.0.1 fixes HEVC buffer corruption and stream performance. DAT 1.0.0 was released 2026-09-24; Meta's FAQ says stable rollout began September 30. The iOS README still calls the toolkit developer preview, so use the versioned changelog for individual capability status. Experimental APIs remain subject to change and apps using them cannot yet be published. [Android changelog](https://github.com/facebook/meta-wearables-dat-android/blob/main/CHANGELOG.md), [iOS changelog](https://github.com/facebook/meta-wearables-dat-ios/blob/main/CHANGELOG.md), [FAQ](https://developers.meta.com/wearables/faq/).

The official DisplayAccess sample requires iOS 17.2+, Xcode 26.4+, Swift 6.3+, an Apple development team and a distinct bundle identifier for device builds. Developer Mode does not require Meta app credentials; other release channels use Wearables Developer Center IDs/tokens. Samples and SDK are governed by Meta Developer Terms, not a generic MIT grant. [Sample README](https://github.com/facebook/meta-wearables-dat-ios/blob/main/samples/DisplayAccess/README.md), [license](https://github.com/facebook/meta-wearables-dat-ios/blob/main/LICENSE).

No macOS host, signing capability, account eligibility, release channel, or glasses permission was established by this research. No remote Mac service or account was created.

## Hardware acceptance gate

1. On the owner's account, confirm Web Apps eligibility and install the same authorized HTTPS build that will be tested.
2. Complete authorization without exposing the Gemini key. Check composer behavior separately from desktop keyboard behavior.
3. Navigate every control using band/captouch, submit handwritten text once, observe backend receipt and a genuine model answer on the display.
4. Reopen the app and verify conversation identity, session expiry, long-answer navigation and connection failures.
5. Upload an image using the documented phone/desktop fallback; select that stored image on glasses, ask a follow-up, replace it, and delete it.
6. In a separate native spike, test registration, camera permission, actual image bytes, background/lock behavior, disconnects and display output on pinned SDK/firmware versions before proposing a unified camera workflow.

The official simulator can preview layout and navigation, but cannot certify real handwriting, surroundings, wearable inputs, camera transport or background reliability. [Testing](https://wearables.developer.meta.com/docs/develop/webapps/test/).
